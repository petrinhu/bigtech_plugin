## 4. Windows UTF-8 / ASCII-safe stdout

### O que quebrou

Run **#11** `31990526503` SHA `cd5cb771da5f23ff5e353f7c2c69481208dfcd6f` (`docs(bt-9)` **depois** do feat `b9bd2ee`, **antes** do fix):

| Job | Step evals | Conclusão |
|---|---|---|
| `validate (windows-latest, py3.11)` `95273123737` | `evals roteamento /bigtech (BT-8)` | **failure** |
| `validate (windows-latest, py3.12)` `95273123761` | idem | **failure** |
| Ubuntu 3.11/3.12 + debian/fedora/arch + gitleaks | evals | success |

Causa no commit de fix (objeto `4e8843f`): print da policy com U+2192 (`solo→early`) sob cp1252 → `'charmap' codec can't encode character '\u2192'`.

`git show b9bd2ee:evals/bigtech_routing/run_evals.py`: `solo→early` no print; **sem** `reconfigure`.

### O que o fix entrega (blob `10a59ea5`)

1. **Stdout sem `→` problemático.** A policy impressa é `solo->early` (ASCII). Comentário L307: `Windows CI default (cp1252) cannot encode U+2192`.
2. **`_ensure_utf8_stdio()`** (L324–330) chama `stream.reconfigure(encoding="utf-8", errors="replace")` em stdout/stderr, swallow de `Exception`. Invocado no início de `main()`.

U+2192 **permanece** só em docstring/comentários (7 ocorrências: L85, L131, L147, L150, L162, L193 + o comentário L307 cita o codepoint sem emitir o glifo na string de print). README e `cases.json` notes também têm `→`; **não** passam pelo `print` do harness.

### Simulação cp1252 (reconfigure desligado)

`run()` chamado com stdout/stderr que fazem `.encode('cp1252')` e `reconfigure` levanta `OSError`:

| Checagem | Resultado |
|---|---|
| rc | **0** |
| stdout encodável em cp1252 | **YES** (817 chars) |
| U+2192 no stdout | **False** |
| `solo->early` no stdout | **True** |
| linha resultado | `resultado: 10/10 PASS, 0 FAIL` |

Ou seja: o harness **não depende** do `reconfigure` para sobreviver ao Windows. O ASCII no print é o conserto real; o reconfigure é cinto.
